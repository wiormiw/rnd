# Technical Specification: Learning System & Remediation Engine (RnD)

This document describes the architecture, database schema, engines, Redis usage and API of the local curriculum and flashcard system. It describes the implemented code. Where the original plan and the code differ, the code is correct and the difference is listed in section 7.

---

## 1. System Overview

The system runs locally without artificial intelligence models or cloud services. It uses explicit algorithms and relational state to manage a curriculum of topics with prerequisites, schedule flashcard reviews with SM-2, select a daily sprint with a knapsack, and turn failed recall into practice tasks.

### Core Objectives
- **Curriculum DAG:** Topics form a prerequisite graph. Cycles are rejected, and a topic unlocks only when its direct prerequisites are mastered.
- **SM-2 Engine:** Each flashcard keeps its own SM-2 state, updated from an explicit quality score (0 to 5).
- **Knapsack Scheduler:** The daily sprint selects the most urgent due cards that fit a time budget, deterministically.
- **Remediation Pipeline:** A review below the threshold creates a practice task and suspends the card until the task is completed.

### Out of Scope (for now)
- Flutter client. It needs authentication before it is exposed beyond the local network.
- Google Keep import (Takeout JSON).
- Caching of any kind. The sprint is computed per request.

## 3. Database Schema

Schema source: `src/database/schema.ts`. Migrations are in `drizzle/`. All timestamps are `timestamptz`. Primary keys are UUIDs generated by the database.

### 3.1 `topics`

| Column | Type | Constraints |
| :--- | :--- | :--- |
| `id` | uuid | primary key |
| `title` | text | not null |
| `description` | text | not null, default `''` |
| `created_at` | timestamptz | not null, default now() |
| `updated_at` | timestamptz | not null, default now(), set on every update |

### 3.2 `topic_prerequisites` (DAG edges)

| Column | Type | Constraints |
| :--- | :--- | :--- |
| `topic_id` | uuid | FK to `topics.id`, on delete cascade. The topic that depends on the prerequisite. |
| `prerequisite_id` | uuid | FK to `topics.id`, on delete cascade |

- Primary key `(topic_id, prerequisite_id)`.
- Check constraint `topic_prerequisites_no_self`: `topic_id <> prerequisite_id`.
- Index on `prerequisite_id`.

### 3.3 `memos`

| Column | Type | Constraints |
| :--- | :--- | :--- |
| `id` | uuid | primary key |
| `title` | text | not null |
| `body` | text | not null, default `''` |
| `topic_id` | uuid | nullable FK to `topics.id`, on delete set null |
| `created_at` | timestamptz | not null, default now() |

Index on `topic_id`. Memos are raw notes. A memo may link to one topic.

### 3.4 `cards`

| Column | Type | Constraints |
| :--- | :--- | :--- |
| `id` | uuid | primary key |
| `topic_id` | uuid | not null, FK to `topics.id`, on delete cascade |
| `memo_id` | uuid | nullable FK to `memos.id`, on delete set null. The memo the card came from. |
| `front` | text | not null |
| `back` | text | not null |
| `estimated_minutes` | integer | not null, default 2, check `>= 1` |
| `priority_weight` | double precision | not null, default 1, check `> 0` |
| `sm_interval` | integer | not null, default 0 (days) |
| `sm_repetition` | integer | not null, default 0 |
| `sm_ease_factor` | double precision | not null, default 2.5, check `>= 1.3` |
| `next_review_at` | timestamptz | not null, default now() |
| `created_at` / `updated_at` | timestamptz | not null, default now() |

Indexes on `next_review_at` and `topic_id`.

Scheduling fields (`sm_*`, `next_review_at`) and `topic_id` are server-owned. The card API rejects them in the request body.

### 3.5 `review_logs` (append-only)

| Column | Type | Constraints |
| :--- | :--- | :--- |
| `id` | uuid | primary key |
| `card_id` | uuid | not null, FK to `cards.id`, on delete cascade |
| `quality_score` | integer | not null, check `between 0 and 5` |
| `time_spent_seconds` | integer | not null, check `>= 0` |
| `previous_interval` / `new_interval` | integer | not null |
| `previous_ease_factor` / `new_ease_factor` | double precision | not null |
| `reviewed_at` | timestamptz | not null, default now() |

Index on `(card_id, reviewed_at)`.

### 3.6 `action_items` (remediation output)

| Column | Type | Constraints |
| :--- | :--- | :--- |
| `id` | uuid | primary key |
| `card_id` | uuid | not null, FK to `cards.id`, on delete cascade |
| `title` | text | not null. Format: `Practice: ` followed by the card front, truncated to 180 characters. |
| `status` | enum `action_item_status` (`PENDING`, `DONE`) | not null, default `PENDING` |
| `spawned_at` | timestamptz | not null, default now() |
| `completed_at` | timestamptz | nullable, set when completed |

- Partial unique index `action_items_one_pending_per_card` on `(card_id) WHERE status = 'PENDING'`. A card has at most one pending task.
- Index on `status`.

## 4. Redis Usage

Redis is used for one thing: rate limiting. The readiness check also pings it.

| Key | Data Structure | Purpose |
| :--- | :--- | :--- |
| `rl:global:{ip}` | Hash (token bucket, Lua) | Per-client-IP request budget for every route except `/health*`. Capacity 60, refill 1 token per second by default. |

All keys are prefixed with `REDIS_KEY_PREFIX` (default `rnd:`).

Fail-open behaviour: if Redis does not answer within `RATE_LIMIT_TIMEOUT_MS`, requests are allowed when `RATE_LIMIT_FAIL_OPEN=true` (the default) and answered with 503 otherwise.

### Not implemented

The original design added three Redis caches. They are deliberately not built:

| Planned key | Original purpose | Why not |
| :--- | :--- | :--- |
| `rnd:sprint:active:{date}` | Cache the daily sprint for 24 hours | Single user, and the sprint is cheap to compute. A cache needs invalidation on every review, which is an avoidable source of stale results. |
| `rnd:graph:unlocked_set` | Memoise the unlocked topics | The unlocked set is derived from the same snapshot the request already reads. |
| `rnd:lock:scheduler` | Prevent concurrent sprint calculations | Nothing is written by the sprint. Two concurrent requests compute the same result. |

If load ever justifies a cache, add it with the invalidation rules written first.

## 5. Pure Mathematical Engines

Source: `src/engines/`. These modules import nothing from NestJS and do no I/O. They take `now: Date` as a parameter and never read the clock.

### 5.1 SuperMemo-2 (SM-2)

```typescript
calculateSM2(
  state: { interval: number; repetition: number; easeFactor: number },
  qualityScore: number,   // integer 0..5, otherwise RangeError
  now: Date,
): { interval: number; repetition: number; easeFactor: number; nextReviewAt: Date }
```

Rules:
1. Ease factor: `EF' = max(1.3, EF + (0.1 - p × (0.08 + p × 0.02)))`, where `p = 5 - q`.
2. If `q >= 3`: interval is 1 when repetition is 0, 6 when repetition is 1, otherwise `round(interval × EF')`. Repetition increases by 1.
3. If `q < 3`: repetition resets to 0 and interval to 1.
4. `nextReviewAt = now + interval × 86_400_000 ms` (whole UTC days).

A new card starts at interval 0, repetition 0, EF 2.5. Its first review sets the interval to 1 (for `q >= 3`).

### 5.2 Urgency

```typescript
urgencyScore(
  card: { nextReviewAt: Date; interval: number; priorityWeight: number },
  now: Date,
): number
```

`urgency = (max(0, daysOverdue) / max(interval, 1) + 1) × priorityWeight`, where `daysOverdue = (now - nextReviewAt) / 86_400_000`. The `max(interval, 1)` avoids division by zero for new cards.

### 5.3 0/1 Knapsack Daily Sprint

```typescript
scheduleSprint<T extends { id: string; estimatedMinutes: number; urgency: number }>(
  candidates: readonly T[],
  maxMinutes: number,
): T[]
```

- Value is urgency. Weight is `estimatedMinutes`. Capacity is `floor(maxMinutes)`.
- Candidates are sorted by urgency descending, then id ascending. Only the first `MAX_CANDIDATES = 2000` are considered. The rest are dropped silently, lowest urgency first.
- The DP uses a `Float64Array` of values and a `Uint8Array` keep-table (`n × (capacity + 1)`) for backtracking.
- Returns the selected items in the sorted order. Ties are resolved by id, so the result is deterministic.
- Returns `[]` when capacity is not positive or there are no candidates.

### 5.4 Curriculum DAG

```typescript
wouldCreateCycle(edges: readonly Edge[], topicId: string, prerequisiteId: string): string[] | null
topologicalOrder<T extends { id: string; createdAt: Date }>(topics: readonly T[], edges: readonly Edge[]): T[]
unlockedTopicIds(topicIds: readonly string[], edges: readonly Edge[], masteredIds: ReadonlySet<string>): Set<string>
```

- `Edge` is `{ topicId, prerequisiteId }`, meaning `topicId` depends on `prerequisiteId`.
- `wouldCreateCycle`: adding the edge closes a cycle when `topicId` is reachable from `prerequisiteId` along prerequisite edges. Returns the cycle as `[topicId, ..., prerequisiteId, ..., topicId]`, or `null`. A self-edge returns `[topicId, topicId]`. The search is a breadth-first search.
- `topologicalOrder`: Kahn's algorithm. Ties are broken by `createdAt`, then id. Throws if the graph has a cycle (the API prevents this, so the throw is a safety net). Edges that touch unknown ids are ignored.
- `unlockedTopicIds`: a topic is unlocked when every direct prerequisite is in `masteredIds`. A topic with no prerequisites is unlocked.

### 5.5 Mastery

```typescript
isMastered(cards: readonly { id: string; repetition: number }[], pendingCardIds: ReadonlySet<string>): boolean
```

A topic is mastered when every card satisfies `repetition >= 2` and is not in `pendingCardIds`. An empty card list is mastered (`every` on an empty array).

### 5.6 Remediation Threshold

The review service creates a practice task when `qualityScore < 2` (`REMEDIATION_THRESHOLD`). A score of 2 resets the card's SM-2 state but does not create a task.

## 6. API

Base path: `/api/v1`, set by `configure-app.ts`. `/health` and `/health/ready` are excluded from the prefix. Every route except the probes is rate limited. Errors use the shape `{ code, message, details? }`.

### 6.1 Status codes

| Situation | Status |
| :--- | :--- |
| Success with a body | 200 (reads, updates, review, complete) |
| Created | 201 (`POST /memos`, `POST /topics`, `POST /topics/:id/cards`) |
| No content | 204 (deletes, `PUT`/`DELETE` prerequisite) |
| Validation failure (Zod) | 400, `details` is a list of `{ path, message }` |
| Missing resource or unknown route | 404 |
| Business conflict | 409 (prerequisite cycle, pending practice task, action item already done) |
| Rate limited | 429 with `Retry-After` |
| Readiness, dependency down | 503 with per-dependency detail |

### 6.2 Endpoints

The full table with notes is in `README.md`. In summary:

- **Memos:** `POST /memos`, `GET /memos`, `GET|PATCH|DELETE /memos/:id`, `GET /topics/:id/memos`.
- **Curriculum:** `POST|GET /topics`, `GET|PATCH|DELETE /topics/:id`, `PUT|DELETE /topics/:id/prerequisites/:prerequisiteId`, `GET /curriculum/order`.
- **Cards:** `POST|GET /topics/:id/cards`, `GET|PATCH|DELETE /cards/:id`.
- **Reviews:** `POST /cards/:id/review`, `GET /cards/:id/reviews`.
- **Schedule:** `GET /schedule/daily?maxMinutes=` (1–480, default 45).
- **Action items:** `GET /action-items?status=`, `POST /action-items/:id/complete`.
- **Health:** `GET /health`, `GET /health/ready`.

Response shapes:
- Topic: the topic row plus `prerequisiteIds`, `cardCount`, `mastered`, `unlocked`.
- Review: `{ card, nextReviewAt, actionItem }`. `actionItem` is `null` when no task was created.
- Daily sprint: `{ generatedAt, maxMinutes, totalCards, allocatedMinutes, items: [{ card: { id, topicId, front, back, estimatedMinutes }, urgency }] }`.
- Paginated lists: `{ items, total, limit, offset }`. Memo, card, review, and action-item lists are paginated. Topic lists are not.

### 6.3 Transaction Boundaries

Each rule that must not interleave runs in one database transaction. The service decides, and the repository commits.

**Review (`POST /cards/:id/review`)**
1. Begin a transaction.
2. `SELECT ... FOR UPDATE` on the card row. Missing card: 404.
3. If a `PENDING` action item exists for the card, roll back and return 409 with its id.
4. Compute the SM-2 update (pure function, runs while the row is locked).
5. Insert the `review_logs` row.
6. If `qualityScore < 2`, insert a `PENDING` action item.
7. Update the card's SM-2 state and `next_review_at`.
8. Commit.

The partial unique index on `action_items` guards against two pending tasks for one card even if the lock were bypassed.

**Add prerequisite (`PUT /topics/:id/prerequisites/:prerequisiteId`)**
1. The service checks that both topics exist, and rejects a self-edge with 409.
2. Begin a transaction. Take `pg_advisory_xact_lock(7204311)`. This key serialises all prerequisite inserts.
3. Load all edges. Run `wouldCreateCycle`. A cycle returns 409 with the path, and nothing is written.
4. Insert the edge with `ON CONFLICT DO NOTHING`.
5. Commit. The lock is released at commit.

The lock means two concurrent requests cannot each pass the cycle check and then together close a cycle.

**Complete action item (`POST /action-items/:id/complete`)**
1. Begin a transaction.
2. `SELECT ... FOR UPDATE` on the item. Missing: 404. Already `DONE`: 409.
3. Set the item to `DONE` with `completed_at = now`.
4. Set the card's `next_review_at = now`, which makes it due and returns it to the sprint.
5. Commit.

## 7. Decisions

Fixed in the design plan. The code follows them, with the differences noted below the table.

| Topic | Decision | Why |
|---|---|---|
| Unlock rule | A topic is **unlocked** when every *direct* prerequisite is **mastered**. Topics with no prerequisites are always unlocked. | Simple, predictable. |
| Mastered | Every card in the topic has `smRepetition >= 2` (passed twice in a row) and no pending action item. **A topic with no cards counts as mastered**, so grouping topics never block. | Avoids topics that can never unlock. |
| New cards | `interval 0, repetition 0, EF 2.5, nextReviewAt = now`, so new cards are due right away. | Matches SM-2 start state. |
| Remediation | Score `< 2` creates one `PENDING` action item. The card is **suspended**: it is left out of sprints and reviews return 409 until the item is completed. Completing it sets the card's `nextReviewAt = now`. At most one pending item per card (partial unique index). | Return to normal SM-2 after the practice task. |
| Review time | `timeSpentSeconds` (int, 0 to 86400), not minutes. | Flashcard reviews take seconds. |
| Sprint cache | **No Redis cache.** Compute on every request. | Single user, cheap computation. |
| API prefix | `/api/v1`, with `/health*` excluded. | Versioned before the Flutter client exists. |
| Clock | Engines take `now: Date` as a parameter and never call `new Date()`. Days are whole UTC days (`interval × 86_400_000 ms`). The service reads the injected `CLOCK` once per request. | Deterministic tests. |
| Memos | Raw notes. A memo may link to one topic. A card may cite one memo. Cards are written by hand. | Keeps notes and reviewable items separate. |

**Differences from the original plan, where the code is the reference:**
- The SM-2 signature is `calculateSM2(state, qualityScore, now)`, not `calculateSM2({ ..., qualityScore }, now)`.
- The review response sets `actionItem` to `null` when no task is created. It is not omitted.
- The daily sprint response also carries `generatedAt` and `maxMinutes`.
- The `invalid` error code maps to 422 in `STATUS_BY_CODE`, but Zod validation failures return 400. Nothing raises the `invalid` error code.

1. **Phase 1: Environment & Schema (done).** NestJS project with TypeScript. Drizzle migrations on `postgres.js`. Redis client with reconnect. Validated configuration.
2. **Phase 2: Math Engine & Unit Tests (done).** SM-2, urgency, knapsack, DAG and mastery, with unit tests.
3. **Phase 3: Routes & Transaction Boundaries (done).** Curriculum, cards, reviews, daily sprint and action items, with the transactions in section 6.3. Rate limiting and health checks.
4. **Phase 4: Client (next).**
   - Flutter client. Authentication is required before the API is exposed beyond the local network.
   - Google Keep import from Takeout JSON.
   - OpenAPI description of the API, for the client.

### Known gaps
- The three transactions in section 6.3 are covered by `src/__test__/db.integration.test.ts`, which runs only when `DB_TEST_URL` is set. It is not part of the default `pnpm test` run.
